# TDD Rule

> **⚠️ 이 규칙은 Rigid — 상황에 맞게 변형하지 마라.**
> 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"를 만들지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 **기본값(fallback)**이다. 프로젝트 규칙이 없거나 침묵하는 부분에만 적용한다.

## 1. 적용 기준

### 반드시 TDD를 적용한다
- 비즈니스 로직
- API (핸들러, 엔드포인트, 클라이언트 로직)
- 유틸 함수
- 버그 수정 (**먼저 버그를 재현하는 실패 테스트를 작성한다**)

### TDD가 불필요하다
- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업·스타일)
- SQL

애매하면 **적용한다.**

## 2. RED-GREEN-REFACTOR

### RED — 실패하는 테스트 작성
- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 테스트가 아니다.
- 실패 이유는 **"기능 미구현"**이어야 한다. 오타·import 오류·문법 오류로 실패했다면 테스트를 고쳐서 다시 RED를 만든다.

### GREEN — 통과시키기
- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 지금 테스트가 요구하지 않는 기능·옵션·분기는 쓰지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 실행해서 확인한다.

### REFACTOR — 정리
- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **모든 테스트가 green인 상태를 유지한다.** 수정할 때마다 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 한다.

### 반복
- 다음 동작이 남아 있으면 **RED로 돌아간다.**

## 3. 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성했다면 **그 코드를 삭제하고 RED부터 다시 시작한다.**
- **"참고용"으로 남기는 것도 금지한다.** 주석 처리, 임시 파일, 별도 브랜치 보관, 복사해 두고 보기 모두 포함한다.
- 삭제한 코드를 보고 다시 타이핑하지 않는다. 테스트가 요구하는 것만 새로 쓴다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드는 테스트도 단순하다. 30초면 쓴다. 단순한 코드가 가장 자주 조용히 깨진다. |
| "나중에 추가하겠다" | 나중에 쓴 테스트는 이미 통과한다. 실패를 본 적 없는 테스트는 아무것도 증명하지 못한다. |
| "시간이 없다" | 디버깅과 회귀 수정이 더 오래 걸린다. 급할수록 안전망이 필요하다. |
| "삭제하면 낭비" | 매몰 비용 오류다. 검증되지 않은 코드를 유지하는 비용이 다시 쓰는 비용보다 크다. |
| "프로토타입이다" | 프로토타입은 프로덕션이 된다. 버릴 코드라면 어차피 삭제 비용도 없다. |

## 완료 체크

- [ ] 모든 새 동작에 먼저 실패한 테스트가 있다
- [ ] 각 실패는 "기능 미구현" 때문이었다
- [ ] 전체 테스트가 green이다
- [ ] 테스트 없이 작성된 프로덕션 코드가 남아 있지 않다

하나라도 체크하지 못하면 **완료가 아니다.**
