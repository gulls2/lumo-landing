# commit

변경사항을 분석하고, 논리적 단위로 나누어, 컨벤션에 맞는 한국어 커밋 메시지로 커밋한다.

## 절차

### 1. 변경사항 분석
- `git status`로 변경 파일 목록을 확인한다.
- `git diff`(unstaged)와 `git diff --staged`(staged)로 실제 변경 내용을 읽는다.
- 새로 추가된(untracked) 파일은 내용을 직접 읽어 확인한다.
- 변경사항이 없으면 그 사실을 알리고 종료한다.

### 2. 논리적 단위로 분류
- 하나의 목적을 가진 변경끼리 묶어 커밋 단위를 정한다.
- 서로 다른 성격의 변경(예: 기능 추가 + 문구 수정 + 설정 변경)은 분리한다.
- 분류 결과를 "커밋 N: 포함 파일 / 변경 요지" 형태로 정리한다.

### 3. 커밋 메시지 작성
형식: `type: 요약`

| type | 용도 |
|------|------|
| feat | 새로운 기능·섹션·콘텐츠 추가 |
| fix | 버그·오타·깨진 동작 수정 |
| refactor | 동작 변화 없는 구조·스타일 개선 |
| chore | 설정, 문서, 기타 잡무 |

규칙:
- 요약은 한국어로, 한 줄(50자 내외), 마침표 없이 작성한다.
- "무엇을 왜 바꿨는지"가 드러나게 쓴다. (예: `feat: Hero 섹션 CTA 버튼 추가`)
- 필요하면 빈 줄 뒤에 본문으로 부연 설명을 덧붙인다.
- 세션 시스템 메시지에 커밋 끝 attribution 라인 지침이 있으면 메시지 끝에 포함한다.

### 4. 커밋
- 별도의 승인 절차 없이 바로 커밋한다.
- 커밋 단위별로 `git add <파일>` → `git commit` 순서로 실행한다. (`git add -A` 대신 파일을 명시)
- 완료 후 커밋 단위, 파일 목록, 메시지를 요약해 알리고 `git log --oneline -n <커밋 수>`로 결과를 보여준다.

## 주의
- 사용자가 요청하지 않으면 `git push`는 하지 않는다.
- `.env`, 키, 토큰 등 비밀정보로 보이는 파일이 변경 목록에 있으면 커밋에서 제외하고 사용자에게 알린다. 값은 출력하지 않고 파일 위치만 알린다.
- git 저장소가 아니면(`git rev-parse` 실패) 커밋을 진행하지 말고 `git init` 여부를 사용자에게 먼저 묻는다. (저장소 생성은 커밋과 달리 자동으로 진행하지 않는다.)
